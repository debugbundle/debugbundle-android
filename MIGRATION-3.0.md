# Android 3.0 migration

3.0 is the explicit major path from the 2.x synchronous hook and persistence behavior. Keep a pinned 2.x installation available during rollout; the release workflow requires Maven Central artifact and connected-device qualification.

## Capture and hook timing

Public capture signatures, adapters, `DebugBundleBeforeSend`, `DebugBundleQueueStore`, optional indexed acknowledgements, envelope schemas and offline file format remain compatible. Capture performs metadata eligibility and bounded mandatory privacy projection, then admits the protected event in memory. A single coalesced worker on the existing SDK executor performs startup disk hydration, hooks, final privacy/schema/policy checks, sampling and suppression, persistence, transport and acknowledgements. No service or per-event task is created. Admission synchronization covers only bounded queue accounting; callbacks, disk, network and privacy traversal never hold this lock.

`beforeSend` now runs after capture returns. Do not rely on it completing on the calling thread, or use capture's return as a persistence acknowledgement. React Native bridge boolean results indicate local admission, not final hook acceptance or delivery. Valid replacements can change any schema field, including event IDs/types. `null` still drops; invalid results and thrown hooks still use the protected original. The final replacement is checked against current policy and counted/suppressed only after the hook. A disk retry retains the final replacement and does not rerun the hook. Fatal-handler replay keeps its existing hook bypass and clears the crash record only after persistence retains the replay event.

A held hook or custom store can occupy the one worker but cannot hold capture, start replacement workers or accumulate executor tasks per event. Throwable detail extraction uses at most one weak handle per staged event (256 total); staging owns only the protected fixed fallback, not a raw Throwable graph. The worker may inspect one live Throwable transiently. If it has been collected or its getters throw, the fallback is delivered. A held getter/Throwable monitor stalls that worker only. Custom device providers likewise publish protected snapshots from the worker; capture reads the cached snapshot. Custom stores must honor their supplied limits and be safe to call from the worker. User callbacks/custom stores remain responsible for their own allocations and termination.

## Durability and lifecycle

There is now a memory-to-disk window: process termination can lose staged events. Existing persisted events still replay offline. `flush(timeout)` requests delivery and waits for the shared worker generation for at most that timeout; a held callback, store or network operation can outlast the wait. `close()` makes one bounded flush wait and shuts down the executor. These methods are explicit administrative waits; ordinary capture does not call them. Foreground config refreshes coalesce and respect the existing minimum interval.

## Retained data budgets

The staging budget is **256 events and 2 MiB of serialized envelopes**, including pending events, the active hook/persistence batch, prepared replacements and disk retries. Processing removes original batch references incrementally and reserves each replacement before retaining it. One currently executing hook can temporarily return an application-owned replacement before validation/reservation; it cannot expand an entire uncharged batch. Overflow evicts pending lower-priority evidence first; an active entry is protected. Fixed counters summarize queue pressure without retaining rejected payloads.

The offline budget remains independently configurable, default **500 events, 5 MiB and 72 hours**. Built-in stores evict the oldest lowest-priority event on count/byte overflow, preserving FIFO among equal priorities. A lower-priority burst cannot evict an exception. Custom stores keep their existing interface; the SDK withholds an invalid/over-budget hydrated snapshot as a whole to avoid shifting ACK indices.

The offline store and the privacy-safe transport projection are separate retained representations, each bounded by the offline budget. A send snapshot is a list of references to that projection, not another payload clone. During hydration/ACK, the old send snapshot can overlap with the bounded decoded store and newly protected projection. Thus the normal logical retained payload budget is staging plus two offline representations (default **12 MiB**); hydration/ACK may add one offline representation (default **17 MiB**), plus the current single-event privacy/hook projection. Native and external suppression trackers each retain at most500 fixed digest identities with counters; aggregate fingerprints stay compatible. External suppression retains only protocol metadata, capped separately at **500 entries/512 KiB**, never original payload/context. Existing breadcrumb/probe buffers retain their separately configured ring-buffer limits. JSON parsing/serialization and JVM object overhead are additional transient memory, so these serialized limits are not a total JVM heap guarantee. File hydration accepts at most the configured bytes from disk; no full batch of hook replacements bypasses staging accounting.

## Validation before release

Run `make verify` (all module tests, metadata compatibility and per-source-file coverage) and `make smoke` (stage all actual Maven artifacts, check their licenses, and run the fresh consumer). The release workflow also requires connected checks on API 23, 36 and 37.0 before Maven Central publication. Local JVM or artifact checks cannot substitute for those device results.
